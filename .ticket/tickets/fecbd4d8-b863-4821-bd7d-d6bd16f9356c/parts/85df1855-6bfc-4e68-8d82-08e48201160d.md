# Problem

`viewer-ctl prepare <viewer>` shells out to `trunk` and other frontend build
tools. Today the shared subprocess helper only returns a generic exit-status
string on failure. Interactive terminals may still show child stderr/stdout,
but callers that only capture `viewer-ctl`'s own stderr lose the nested cargo
diagnostic, including actionable setup hints like
`rustup target add wasm32-unknown-unknown`.

## Scope

- update the shared subprocess runner in `viewer-ctl` so failures preserve the
  failing command, working directory, exit status, and captured child output
  tail
- keep success-path streaming for prebuild/build/install callers so long-running
  builds still show progress interactively
- update the frontend lifecycle spec and README to document the failure
  reporting contract

## Acceptance criteria

- a failing `viewer-ctl prepare <viewer>` error includes the executed command,
  working directory, exit status, and relevant child stderr/stdout tail
- a nested `trunk -> cargo` failure surfaces actionable guidance to callers
  even when they only receive `viewer-ctl`'s own stderr
- successful frontend builds still stream tool output and return success
